Guide de Documentation UVM

Bienvenue sur le portail de documentation dédié à l'Universal Verification Methodology (UVM) en SystemVerilog. Ce site regroupe les standards, patrons d'architecture et exemples pratiques pour concevoir des environnements de vérification robustes et réutilisables.

Note : Ce projet est configuré pour un déploiement continu et automatique via GitHub Pages et GitHub Actions.

Architecture d'un Testbench UVM

Un environnement de vérification UVM typique structure les composants selon une hiérarchie stricte d'objets et de composants :

  • uvm_test : Instancie l'environnement et configure les tests.
  • uvm_env : Regroupe les agents, scoreboards et modules d'analyse.
  • uvm_agent : Encapsule le sequencer, le driver et le monitor pour une interface donnée.
  • uvm_scoreboard : Compare les résultats observés aux résultats attendus du modèle de référence.

Composants UVM Clés

Chaque composant hérite de uvm_component et participe aux phases de simulation.

Exemple : Driver UVM minimal

my_driver.sv 
class my_driver extends uvm_driver #(my_transaction);
  `uvm_component_utils(my_driver)

  function new(string name = "my_driver", uvm_component parent = null);
    super.new(name, parent);
  endfunction

  virtual task run_phase(uvm_phase phase);
    forever begin
      seq_item_port.get_next_item(req);
      drive_transfer(req);
      seq_item_port.item_done();
    end
  endtask
endclass

Phases UVM

UVM synchronise la construction et l'exécution via des phases automatiques ordonnées :

  1. build_phase : Construction et configuration de la hiérarchie.
  2. connect_phase : Connexion des ports TLM et interfaces virtuelles.
  3. end_of_elaboration_phase : Derniers réglages de topologie.
  4. run_phase : Phase consommatrice de temps (tâches temporelles).
  5. check_phase / report_phase : Validation des résultats et génération du rapport final.

Factory et uvm_config_db

La Factory permet d'enregistrer des composants et de surcharger dynamiquement des types lors des tests sans modifier le code source existant :

override_example.sv 
// Surcharge d'un driver par un driver d'erreur pour un test spécifique
set_type_override_by_type(my_driver::get_type(), error_driver::get_type());

Sequences & Stimuli

Les séquences séparent la génération de scénarios de stimuli du protocole de transmission physique (géré par le driver).

Ports & Communication TLM

Les interfaces Transaction Level Modeling (TLM) assurent un couplage faible entre le monitor, les agents et le scoreboard grâce à des ports et exports (uvm_analysis_port, uvm_analysis_imp).
